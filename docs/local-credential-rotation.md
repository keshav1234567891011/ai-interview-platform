# Controlled local credential rotation

Potentially exposed local PostgreSQL, JWT and obsolete bootstrap credentials are treated as compromised. No existing credential is silently changed. The user reported that the PostgreSQL role may be shared and requested it be left unchanged; PostgreSQL/JWT rotation is therefore blocked pending scope confirmation and approval. A missing independent settings encryption key was generated privately with approval; an existing one is never overwritten. The explicitly requested obsolete bootstrap variable was removed after verifying completed owner setup, preserving all other environment values and without invalidating sessions or modifying the actual owner password.

1. Establish that the configured PostgreSQL role is dedicated to InterviewAI. A role password is cluster-wide and can affect other clients/databases using that role. Do not inspect unrelated projects or rotate a shared role without explicit authorization. If scope remains unclear, the operator must confirm it or deliberately provision a dedicated role and approve the application-only transition.
2. Obtain approval for a brief local service interruption and invalidation of all application sessions. Preserve the actual owner password, account state and all application data. Never rerun bootstrap or password recovery.
3. Pause only known project services under an owned launcher; leave unknown/unrelated processes untouched. Record rollback dependencies privately without creating printable secret copies or tracked environment backups.
4. Generate fresh strong credentials privately. Change only the approved dedicated database role password through a secure non-logging input path; never embed a plaintext password in SQL/shell arguments/history. Update only the password portion of the ignored application's `DATABASE_URL`, URL-encoding it correctly. The PostgreSQL password change and app configuration change must be coordinated; do not modify another role or database.
5. Replace only the ignored `JWT_SECRET` with a fresh independent random secret of at least 32 bytes. This invalidates existing application sessions after backend restart; it does not change owner/admin password hashes. Do not reuse the JWT secret as the settings encryption key. Preserve any encryption key protecting stored API credentials.
6. Remove obsolete `OWNER_BOOTSTRAP_PASSWORD` after confirming initial owner setup is complete. Existing owner authentication does not use this variable. Leave unrelated `.env` entries unchanged. The cancelled recovery workflow does not require `OWNER_RESET_PASSWORD`; do not introduce or use it.
7. Restart through root `npm run dev`. `.env` edits alone are not guaranteed to reload cached settings; ensure the known backend process is restarted. Verify `/health`, `/ready`, frontend API proxy, normal user-controlled owner login and unchanged owner role/first-password-change state. Do not test by reusing or displaying the obsolete bootstrap password.
8. If verification fails, stop affected operations and use the pre-approved private rollback procedure; never print connection strings or reset accounts to make the check pass. Confirm `.env` remains ignored/untracked and that Git contains no secret material.

Production must use fresh independent secrets, not copied local development credentials. Rotation and external infrastructure changes require their own explicit approval; ordinary source/test work can continue independently.
